## 实践中的含义

如果你发布修改后的 Kumo — 包括通过网络服务 — 你必须:

1. 向用户提供修改后的源代码。
2. 对结果保持 AGPL-3.0-only 许可证。
3. 保留版权声明。

如果你仅个人使用 Kumo,许可证不要求你发布任何内容。

如果你 fork 以回馈上游,你已经受保护:你的 PR 携带与项目其余部分相同的
许可证。

## 贡献者许可

通过提交 pull request,你同意你的贡献在与项目其余部分相同的 AGPL-3.0-only
条款下获得许可。我们不需要单独的 CLA。

如果你的雇主对你的工作主张权利,请在提交前解决该问题。我们无法接受
贡献者无权许可的 PR。

## 第三方组件

Kumo 捆绑或与几个上游项目通信。每个都有自己的许可证:

- **[Mihomo](https://github.com/MetaCubeX/mihomo)** — 代理核心。
  GPL-3.0。Kumo 将其作为子进程生成;**并非**静态链接。
- **[Sub-Store](https://github.com/sub-store-org/Sub-Store)** — 订阅管理
  sidecar。按其自有条款分发。Kumo 捆绑 Node 运行时和生成的
  `sub-store.bundle.js`。
- **[swift-argument-parser](https://github.com/apple/swift-argument-parser)**
  — Apache 2.0。
- **[Yams](https://github.com/jpsim/Yams)** — MIT。

汇总声明见
[docs/THIRD_PARTY_NOTICES.md](https://github.com/ProjectKumo/KumoApp/blob/main/docs/THIRD_PARTY_NOTICES.md)。

<Callout type="warn">
"捆绑"在该列表中是有实际意义的。如果你发布修改后的 Kumo,请重新检查每个
上游的条款 — 义务并非完全相同。
</Callout>

## 你不能做什么

AGPL 的目的是保持修改的开放性。以下几件事违背许可证的精神(且可能违背
字面含义):

- 发布 Kumo 的闭源 fork。
- 移除 AGPL 声明或版权头。
- 以不同许可证重新发布 Kumo 的源代码。
- 使用 "Kumo"、"KumoApp" 或 Kumo logo 来暗示对衍生项目的认可。为你的
  fork 使用不同的名称和品牌。

## 你能做什么

- 从源码构建 Kumo。
- 为个人或内部使用而修改。
- 通过 pull request 分享补丁。
- 为团队运行私有构建,并向该团队提供源代码。
- 代表他人运行 Kumo — 前提是你向这些用户提供修改后的源代码。

如果不确定你的用例是否合规,在讨论或 issue 中询问。我们宁愿帮助也不愿
诉讼。
